# ADR-003: Seller-owned vs courier-owned status ranges on a shared `Order` lifecycle, with `fulfillmentType` branching

## Status
Accepted

## Context

An `Order` now needs states the bakery controls (being prepared, ready) in addition to the courier states that already exist (`ACCEPTED`, `PICKED_UP`, `DELIVERED`) plus `PENDING` and `CANCELED`. Two different actors — the bakery and the courier — advance the same order, and a `PICKUP` order has no courier at all.

Options for representing this:

- One `status` field with all states, plus rules about who may make which transition.
- Two fields: a `prepStatus` owned by the seller and a `deliveryStatus` owned by the courier.
- A generic state-machine/event-log table.

The existing enum in Prisma is `OrderStatus { PENDING, ACCEPTED, PICKED_UP, DELIVERED, CANCELED }`. The domain type in `src/core/entities/orders.ts` additionally lists `ACTIVE`, which is not in the Prisma enum and is unused — dead.

## Decision

**One `status` field**, extended to `PENDING → PREPARING → READY → ACCEPTED → PICKED_UP → DELIVERED` (+ `CANCELED`), with an **actor-aware, fulfillment-aware transition table** in a pure core module.

- Prisma `OrderStatus` enum gains `PREPARING` and `READY`. The unused `ACTIVE` is removed from the domain type (verified unused); the Prisma enum is left without it (it was never there).
- A core module `src/core/usecases/orders/order-status-transitions.ts` exports a function that, given `(from, to, actor, fulfillmentType)`, either returns cleanly or throws `InvalidOrderStatusTransitionError` (a new 422 `AppError` subclass).
- **Seller-allowed transitions** (`actor: 'seller'`, caller's bakery owns the order):
  - `PENDING → PREPARING`
  - `PREPARING → READY`
  - `PENDING → CANCELED`, `PREPARING → CANCELED`, `READY → CANCELED` (only while no courier has claimed it; enforced by also checking `deliveryPersonId == null` for a `DELIVERY` order)
  - `PICKUP` only: `READY → PICKED_UP` — the seller confirms the customer collected it; this is the terminal state for a pickup order (no `ACCEPTED`, no `DELIVERED`).
- **Courier-allowed transitions** (`actor: 'courier'`, `fulfillmentType: 'DELIVERY'`, caller owns the claim):
  - `READY → ACCEPTED` (claim — via the dedicated accept endpoint, not the generic status patch)
  - `ACCEPTED → READY` (release — via the dedicated release endpoint)
  - `ACCEPTED → PICKED_UP`
  - `PICKED_UP → DELIVERED`
- `fulfillmentType` is stored on both `Subscription` (the template's default, set at subscription creation) and `Order` (the instance's own value, copied at generation). An order's `fulfillmentType` is immutable after generation.
- `READY` is the release point:
  - `DELIVERY` + `READY` + `deliveryPersonId == null` ⇒ the order is in the courier available pool; marking `READY` emits `order-available` over `sseService`.
  - `PICKUP` + `READY` ⇒ collectable by the customer; no courier pool involvement.

## Alternatives Considered

1. **Two status fields (`prepStatus`, `deliveryStatus`).** Rejected: the two ranges are strictly sequential (a courier can't accept an order that isn't `READY`), so a single ordered status expresses the real world with less room for contradictory combinations (`prepStatus: PENDING` + `deliveryStatus: DELIVERED`). The delivery feature also already reads a single `status`.
2. **Generic state-machine table / event log.** Rejected: over-engineered for six states and two actors; nothing else in this codebase works that way.
3. **Add a `COLLECTED` status for pickup instead of reusing `PICKED_UP`.** Rejected: the user's decision was to add `PREPARING` + `READY` only; `PICKED_UP` already means "left the bakery's hands", which fits customer collection. Documented so the semantics are clear.

## Consequences

**Positive**
- One ordered status, one place (the transition module) that defines every legal move and who may make it — used by both the seller status use case and the courier status use case.
- `PICKUP` and `DELIVERY` share the model but diverge exactly where they must.
- The delivery feature's existing single-`status` reads keep working.

**Negative / costs**
- Every transition now goes through the transition module; a missed call site could allow an illegal move. Mitigated by there being only two write paths for status (seller use case, courier use case) plus the two dedicated accept/release endpoints.
- Reusing `PICKED_UP` as the pickup terminal is a semantic stretch that must be documented (done here and in `docs/architecture.md`).
- The seller's `CANCEL` window depends on both `status` and `deliveryPersonId`, a two-field precondition the use case must check together.
