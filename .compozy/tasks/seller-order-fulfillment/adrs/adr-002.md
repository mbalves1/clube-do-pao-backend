# ADR-002: Snapshot order line items at generation time

## Status
Accepted

## Context

An `Order` is generated from a `Subscription` whose basket is a set of `SubscriptionItem` rows, each pointing at an `Item` (`name`, `priceCents`, `available`) owned by the bakery. When the bakery later looks at an order, and when any future phase computes a total, it needs to know what was in that order.

`Item` is mutable: the bakery edits names and prices, and toggles availability, through the existing item-management flow. If an order simply referenced the live `Item` rows:

- Renaming or repricing an item would retroactively rewrite every past order that contained it.
- Deleting an item would leave historical orders pointing at nothing.
- A total computed on a delivered order would change days later.

## Decision

At generation time, copy each basket line into an `OrderItem` row that stores its own `nameSnapshot` and `priceCentsSnapshot` alongside `itemId` and `quantity`.

- `OrderItem.itemId` is kept (for traceability / "reorder this" later) but is **not** the source of display data.
- `OrderItem.nameSnapshot` and `OrderItem.priceCentsSnapshot` are the values read from the `Item` row **at the moment the order is generated**, and never updated afterward.
- `OrderItem.quantity` comes from `SubscriptionItem.quantity`.
- The generation use case reads the item values via the template query (which joins the basket to `Item`), so no separate `ItemRepository` dependency is needed inside generation.
- If an item in the basket has been deleted before generation runs, that line is skipped and generation continues (logged in the result count); it does not abort the whole order.

## Alternatives Considered

1. **Reference live `Item` only, compute everything on read.** Rejected: retroactive mutation of historical orders is unacceptable for anything that will later carry money.
2. **Snapshot only the price, keep the name live.** Rejected: half-measure; a renamed item still makes an old order read wrong, and the two fields cost the same to store.
3. **Full JSON blob of the item on the order line.** Rejected: only `name` and `priceCents` are needed for display/records in this phase; a blob invites schema drift and is harder to query. Add fields later if a real need appears.

## Consequences

**Positive**
- A past order is immutable regardless of catalog edits.
- Generation has no dependency on `ItemRepository` — it reads through the subscription-template query.
- Future totals/settlement can trust `priceCentsSnapshot`.

**Negative / costs**
- Item data is duplicated onto every order line; a name/price "correction" does not propagate to already-generated orders (this is the intended behavior, but support staff must understand it).
- `OrderItem` and `SubscriptionItem` are two similar-looking tables; the distinction (template basket vs snapshotted instance line) must be documented in `docs/architecture.md`.
