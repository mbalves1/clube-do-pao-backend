# ADR-001: Split `Subscription` (recurring template) from `Order` (per-service-date instance)

## Status
Accepted

## Context

Clube do Pão's domain has always described two things — a recurring arrangement between a customer and a bakery, and a concrete fulfillment on a given day — but the code only ever built one table for both:

- `create-subscribe.ts` takes a date range + `daysWeek` and writes **one `subscription` row per matching service date**. A "subscription" row is therefore already a single dated occurrence, not a template.
- `delivery-order-assignment` treats those `subscription` rows as the orders: `findAvailable`, `claim`, and `release` all run `prisma.subscription.updateMany(...)` setting `subscription.deliveryPersonId` and `subscription.status`.
- The `Order` table exists but is written only as a lazy side effect inside `UpdateOrdersUseCase` when a courier hits `PATCH /orders/:orderId/:deliveryId`, and even then it is half-synced with the `subscription` row.

This blocks the seller order-fulfillment feature:

- There is nowhere to hang **line items** (which products, how many) for a fulfillment — a subscription row has a free-text `notes` and nothing else.
- There is nowhere to put a per-fulfillment **`fulfillmentType`** distinct from the recurring arrangement's default.
- The **status** field on `subscription` is overloaded: it means both "subscription lifecycle" (`ACTIVE`, `PAUSED`, `CANCELED`) and "this day's order lifecycle" (`PENDING`, `ACCEPTED`, ...). Adding seller states (`PREPARING`, `READY`) to it deepens the overload.
- A bakery-scoped query for "today's orders for my bakery" against `subscription` is really a query for occurrences, mixed with template-lifecycle rows.

## Decision

Make `Order` the per-service-date instance and system of record for a fulfillment, generated from a `Subscription` that becomes a recurring template.

- **`Subscription`** keeps the customer↔bakery arrangement: `userId`, `bakeryId`, cadence (`frequency`, `daysWeek`), service/delivery windows, `notes`, a new `active` flag, and a new default `fulfillmentType`. It gains a `SubscriptionItem[]` basket. Its `serviceDate`, `status`, and `deliveryPersonId` columns become **legacy** — retained for backfill/history, no longer written by any new-flow code.
- **`Order`** carries: `subscriptionId`, denormalized `bakeryId` (for the bakery-scoped query without a join through subscription), `serviceDate`, `fulfillmentType`, the full lifecycle `status` (now including `PREPARING`, `READY`), lifecycle timestamps (`preparingAt`, `readyAt`, `acceptedAt`, `pickedUpAt`, `deliveredAt`, `canceledAt`), `deliveryPersonId`, and an `OrderItem[]` snapshot of the basket.
- A unique constraint on `Order(subscriptionId, serviceDate)` makes generation idempotent.
- A one-off **data migration** backfills one `Order` per existing `subscription` row (copying `serviceDate`, `bakeryId`, mapped `status`, `deliveryPersonId`) so the courier flow keeps working the instant its use cases are switched from `SubscribeRepository` to `OrdersRepository`.
- The courier use cases (`ListAvailableOrders`, `AcceptOrder`, `ReleaseOrder`, `UpdateOrders`) are migrated to `Order` within this same feature — not left straddling both models.

## Alternatives Considered

1. **Keep `subscription`-as-order; bolt the seller flow onto it.** Add `PREPARING`/`READY` to the subscription `status`, add `SubscriptionItem`, scope the seller query to `subscription` rows. Smaller (~12–14 tasks), no migration, no courier-flow churn. Rejected: it permanently entrenches the overloaded model, keeps `Order` vestigial and confusing, and every future order feature pays the same tax. The user explicitly chose the clean split over this.
2. **New `Fulfillment` table, leave `Order` untouched as dead code.** Rejected: adds a third noun for the exact concept `Order` already names; `Order` is referenced by `prisma/schema.prisma`, entities, ports, and the delivery feature — reusing it is less disruptive than orphaning it.
3. **Collapse duplicate `subscription` rows into true templates as part of the migration.** Rejected for this phase: risky data surgery (dedupe key is ambiguous), not required to ship the feature. The backfill only *adds* `Order` rows; `subscription` rows are left intact.

## Consequences

**Positive**
- Line items, fulfillment type, and lifecycle status each have exactly one home.
- Bakery-scoped and courier-scoped queries both hit one table with clear semantics.
- `Order` stops being a lazy side effect and becomes explicitly generated.
- One order model across seller and courier flows.

**Negative / costs**
- A data migration is required, and it must run before the courier use cases are switched over — sequencing risk, mitigated by making backfill its own task.
- `Subscription` carries legacy columns (`serviceDate`, `status`, `deliveryPersonId`) that are now inert; they are documented as legacy rather than dropped in this phase to keep the migration reversible.
- `delivery-order-assignment`'s repository methods (`findAvailable`/`claim`/`release` on `SubscribeRepository`) are removed and re-homed on `OrdersRepository`; that feature's ADRs (its ADR-004 optimistic-claim approach) still hold — the conditional `updateMany` pattern just moves to the `order` table.
- Denormalized `Order.bakeryId` must be set correctly at generation and never diverge from `subscription.bakeryId` (it is immutable once set, so low risk).
