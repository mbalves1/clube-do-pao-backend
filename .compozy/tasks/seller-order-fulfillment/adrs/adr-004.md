# ADR-004: Explicit generation trigger for this phase, scheduled generation deferred

## Status
Accepted

## Context

Concrete `Order` rows must be created from the active `Subscription` templates for each service date. The natural production design is a scheduled job (cron / queue worker) that runs once a day and materializes that day's orders. But:

- The repo deploys to Vercel serverless (`docs/stack.md`); there is no always-on process and no scheduler wired up today.
- The generation logic (weekday/`daysWeek`/`frequency` matching, idempotency, item snapshotting) is new and unproven against real subscription data.
- The delivery feature's sibling TechSpec explicitly favors shipping within current infrastructure over introducing new runtime pieces.

## Decision

For this phase, generation is invoked **explicitly** through an authenticated endpoint (`POST /orders/generate`, optional `{ date }` body, default today). It is:

- **Idempotent** — unique constraint on `Order(subscriptionId, serviceDate)`; a re-run creates nothing for rows that already exist and reports `{ created, skipped }`.
- **Gated on `authMiddleware` only** in this phase — no dedicated operator/cron identity, no role guard (the repo has none). Restricting the caller is an explicit open question carried into Phase 2.

Scheduled/automatic generation is deferred to Phase 2, to be added once Phase 1 has run this logic correctly against real subscriptions for a full operating week. The use case is written so a future scheduler can call it directly (it takes a plain `date`, not an HTTP request), so moving to cron later is wiring, not a rewrite.

## Alternatives Considered

1. **Vercel Cron.** Viable, but commits to a scheduling mechanism before the generation logic is validated, and adds a deploy-config surface. Deferred, not rejected — it is the expected Phase 2 path.
2. **Generate lazily on first read of a bakery's queue for a date.** Rejected: hides a write inside a GET, makes the read non-idempotent and slow, and races if two requests hit it at once.
3. **Generate at subscription creation for the whole horizon.** Rejected: `create-subscribe.ts` already over-produces rows this way (one subscription row per date); repeating that mistake for orders would create huge numbers of far-future orders whose item snapshots would be stale by the time they matter.

## Consequences

**Positive**
- Ships within current infrastructure; no scheduler dependency.
- The logic is exercised and observable (call it, inspect `{ created, skipped }`) before automation depends on it.
- The use case signature (`execute({ date })`) is scheduler-ready.

**Negative / costs**
- Until Phase 2, someone/something external must call the endpoint each day, or orders won't exist — operational sharp edge, documented in the PRD.
- The endpoint is callable by any authenticated user this phase; idempotency limits the blast radius to one order per subscription per date, but it should be locked down when scheduling lands.
