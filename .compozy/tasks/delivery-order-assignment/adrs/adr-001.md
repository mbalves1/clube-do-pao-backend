# ADR-001: Self-Service Pull-Based Order Claiming with Real-Time Availability Feed

## Status

Accepted

## Date

2026-07-25

## Context

Today there is no way for a `DeliveryPerson` to see which orders need a courier or to claim one. The only mechanism that assigns a `deliveryPersonId` to an `Order` is a generic `PATCH /orders/:orderId/:deliveryId` endpoint, where `deliveryId` is supplied directly as a URL parameter with no verification that the caller is that delivery person. There is also no listing of unassigned orders anywhere in the product.

We need a product model for how orders move from "needs a courier" to "claimed by a courier," and how much real-time behavior and self-service control to give the courier around that claim.

## Decision

Adopt a **pull-based, self-service claiming model** with a **real-time availability feed**:

- Delivery persons pull a list of all currently unassigned orders (no region/bakery filtering in this phase) and choose which to accept — the system does not push/assign orders to a specific courier.
- When a new order becomes available, a real-time event is emitted (reusing the existing SSE infrastructure and `order-status-updated` pattern) so couriers with the app open see it appear without refreshing.
- A delivery person may release a claimed order back to the pool while it is still `ACCEPTED`; once `PICKED_UP`, the claim is final.
- Only the delivery person who holds the claim may advance that order's status — closing the current gap where any authenticated user can update any order.
- No cap on how many orders a delivery person can hold concurrently in this phase.

## Alternatives Considered

### Alternative 1: Push-based assignment with acceptance timeout

- **Description**: System offers a new order to one specific delivery person with a short countdown (e.g., 5–7 minutes, as observed in iFood/Rappi); on decline or timeout, it offers to the next courier.
- **Pros**: Matches the pattern couriers already know from major delivery apps; can optimize for fairness/proximity later.
- **Cons**: Requires a matching/selection algorithm (who gets offered first?), a queue/timeout mechanism, and a fallback path — all before the project has any concept of courier location, delivery radius, or proximity data. Significant complexity for a first version.
- **Why rejected**: The codebase has no geolocation or proximity data to drive a fair matching algorithm yet. Building the offer/timeout/requeue machinery now would be speculative — YAGNI until there's real usage data on courier availability patterns.

### Alternative 2: MVP without real-time feed (polling only)

- **Description**: Same pull-based claiming model, but couriers only see new orders by manually refreshing/reopening the list — no SSE event on new-order-available.
- **Pros**: Smaller surface area — no new SSE event type to design or maintain.
- **Cons**: Couriers waiting for work would need to poll manually, increasing perceived latency between an order becoming available and being picked up, which directly hurts delivery speed — a core product metric.
- **Why rejected**: The SSE service and event-emission pattern already exist in the codebase (`sseService`, `order-status-updated`); adding one more event type is low incremental cost relative to the UX benefit of instant visibility.

## Consequences

### Positive

- Closes the security/data-integrity gap where any authenticated user can update any order's status.
- Reuses existing SSE infrastructure instead of introducing a new notification channel.
- Simple mental model for couriers: browse, claim, release if needed, deliver.

### Negative

- No fairness or proximity logic — first-come-first-served on the full unassigned pool, which may not scale well once order volume or courier count grows across multiple cities.
- No cap on concurrent claims could let one courier claim more orders than they can realistically deliver, with no system-level protection today.

### Risks

- If order volume grows, a flat "all unassigned orders visible to everyone" list will need geographic filtering — deferred to a later phase, tracked as an Open Question in the PRD.
- Couriers over-claiming and under-delivering is a possible failure mode with no concurrent-order cap; mitigated for now by the release-before-pickup escape hatch.

## Implementation Notes

Out of scope for this ADR — implementation approach (endpoints, schema changes, authorization middleware) belongs in the TechSpec derived from this PRD.
