# ADR-002: Available Orders Feed Sourced from Subscription, 3-Day Window

## Status

Accepted

## Date

2026-07-25

## Context

The existing `GET /orders` endpoint (`ListOrdersUseCase`) does not read from the `Order` table at all — it queries `Subscription` rows for the current day via `SubscribeRepository.getOrderByDay`. The `Order` table is only lazily populated as a side effect of `UpdateOrdersUseCase`, which writes to both `Subscription` (`deliveryPersonId`, `status`) and `Order` (create-or-update, keyed by `subscriptionId`) on every status change. There is no independent source of truth in `Order` that isn't already mirrored on `Subscription`.

The new "available orders" feed needs to decide which table to query and over what date range.

## Decision

Query `Subscription`, not `Order`, filtered by `deliveryPersonId IS NULL` and `serviceDate` within a 3-day window (today through today + 2 days). This extends `SubscribeRepository` with a new method rather than introducing a parallel query path against `Order`.

## Alternatives Considered

### Alternative 1: Query the `Order` table directly

- **Description**: Add a method to `OrdersRepository` that finds `Order` rows with `deliveryPersonId IS NULL`.
- **Pros**: Keeps the "orders" feed conceptually scoped to the `Order` model.
- **Cons**: `Order` rows only exist once a status update has happened at least once (lazy creation in `UpdateOrdersUseCase`). A `Subscription` occurrence that has never been touched has no corresponding `Order` row yet, so querying `Order` would miss most genuinely-available work — the exact orders this feature needs to surface.
- **Why rejected**: Would silently omit the majority of available orders due to the existing lazy-creation behavior.

### Alternative 2: Today-only window (matching `GET /orders`)

- **Description**: Reuse the exact `startOfDay`/`endOfDay` scope already used by `ListOrdersUseCase`.
- **Pros**: Zero new date-range logic; consistent with existing behavior.
- **Cons**: Rejected by the product owner during PRD/TechSpec review in favor of a 3-day planning window.
- **Why rejected**: Product decision — couriers should be able to see a few days ahead.

## Consequences

### Positive

- Single source of truth (`Subscription`) for both the existing "today's orders" list and the new "available" feed — no duplicate/divergent query logic against two tables.

### Negative

- Couples the new feed to the same `Subscription`-as-source-of-truth pattern already used elsewhere, rather than establishing `Order` as the canonical delivery-task record. This is existing technical debt, not introduced by this feature, but not resolved by it either.

### Risks

- If a future refactor moves delivery-task state fully into `Order`, this feed's query will need to move with it. Documented here so that refactor doesn't miss this call site.

## Implementation Notes

Add `SubscribeRepository.findAvailable(startDate: Date, endDate: Date): Promise<Subscription[]>` implemented as `prisma.subscription.findMany({ where: { serviceDate: { gte: startDate, lte: endDate }, deliveryPersonId: null } })`.
