# ADR-005: SSE Availability Notification Scoped to Release Events Only

## Status

Accepted

## Date

2026-07-25

## Context

The PRD requires couriers with the app open to see new available orders in real time. The codebase already has an SSE channel (`sseService`, one event type today: `order-status-updated`, emitted from `OrdersController.updateOrder`). The question is which write paths should trigger the new "order became available" event: only the new release flow, or also `CreateSubscribeUseCase` when a newly created subscription's occurrences fall inside the availability window.

## Decision

Emit a new `order-available` SSE event only from `ReleaseOrderUseCase`, the single point in this feature where an order transitions from claimed back to unclaimed. `CreateSubscribeUseCase` is not modified.

## Alternatives Considered

### Alternative 1: Also emit from `CreateSubscribeUseCase`

- **Description**: When a new `Subscription` occurrence is created with `serviceDate` inside the 3-day availability window, emit `order-available` for it too.
- **Pros**: Covers the case where a customer subscribes and the very next occurrence is claimable immediately, not just tomorrow.
- **Cons**: `create-subscribe.ts` currently has no dependency on `sseService` or any notification concern; wiring it in expands this feature's blast radius into an unrelated use case and its (already timezone/date-loop-heavy) implementation.
- **Why rejected**: Deferred by the product/technical owner to keep this feature's scope to the claim/release lifecycle only. Newly created subscriptions still appear in the feed on next poll/page load — they are just not pushed live at creation time.

## Consequences

### Positive

- Keeps the feature's write-path changes isolated to the new accept/release use cases and the existing order-update use case; `create-subscribe.ts` is untouched.

### Negative

- A courier with the feed open will not see a same-window subscription appear live the moment it's created — only on next fetch/reload, or once any order is later released.

### Risks

- If new-subscription-into-window turns out to be a common real-world case (e.g., customers frequently subscribing for near-term delivery), this gap may need revisiting in Phase 2. Tracked as an Open Question in the PRD update.

## Implementation Notes

`ReleaseOrderUseCase` calls `sseService.emit('order-available', { subscriptionId, bakeryId, serviceDate })` after successfully clearing `deliveryPersonId` and resetting `status` to `PENDING`.
