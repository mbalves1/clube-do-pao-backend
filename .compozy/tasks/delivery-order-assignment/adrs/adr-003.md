# ADR-003: Resolve Delivery Person Identity via Repository Lookup

## Status

Accepted

## Date

2026-07-25

## Context

`authMiddleware` only validates the Supabase JWT and attaches the raw Supabase `User` object (with `app_metadata.role`) to `req.user`. It does not resolve which `DeliveryPerson` row corresponds to the authenticated session, and no role-based authorization guard exists anywhere in the codebase today. The accept, release, and ownership-restricted status-update flows all need to know "which `DeliveryPerson` is this request?" before they can act.

## Decision

Reuse the existing `DeliveryUserRepository.findBySupabaseUserId(supabaseUserId: string): Promise<DeliveryUser | null>` (`src/core/ports/delivery-user-repository.ts:5`, already implemented in `PrismaDeliveryUserRepository`) — no new repository method is needed. Each new use case (accept, release) resolves the `DeliveryPerson` at the start of `execute()` by calling this method with `req.user.id`, and rejects with a `NotFoundError` if no matching `DeliveryPerson` exists (i.e., the authenticated account isn't a courier, or is a courier with no linked Supabase credential — see Blocking Dependency below).

**Blocking dependency**: `findBySupabaseUserId` can only resolve a `DeliveryPerson` whose `supabaseUserId` column is set. Today, `CreateDeliveryUserUseCase` (`src/core/usecases/delivery/create-delivery.ts`) never calls `authGateway.createCredential` — it only inserts a DB row, so `supabaseUserId` is always `null` for delivery persons created through the current registration flow (documented in `docs/architecture.md`, "Autenticação e papéis"). Until delivery-person registration creates a Supabase credential and persists `supabaseUserId`, no delivery person can log in at all, so this feature has no real user to exercise it against. This is a prerequisite, not part of this feature's scope — tracked in the TechSpec's Technical Dependencies.

## Alternatives Considered

### Alternative 1: Dedicated `requireDeliveryPerson` authorization middleware

- **Description**: A new Express middleware, chained after `authMiddleware`, that resolves the `DeliveryPerson` and injects it as `req.deliveryPerson`, rejecting with 403 otherwise.
- **Pros**: Establishes the project's first role-based authorization primitive, reusable by any future delivery-person-only route.
- **Cons**: Introduces a new piece of shared infrastructure and an `Express.Request` type augmentation beyond what this feature strictly needs; the project has exactly two delivery-person routes today (register, and this feature's new ones).
- **Why rejected**: YAGNI for this phase — the repository-lookup approach solves the immediate need with a one-line addition to each use case. A generic role-guard middleware is a reasonable future refactor once more role-restricted routes exist, but speculative here.

## Consequences

### Positive

- Small, additive change — one repository method, called explicitly where needed.
- No new middleware or `Express.Request` type augmentation to maintain.

### Negative

- The "resolve delivery person or reject" check is duplicated in each new use case (accept, release) rather than centralized in one middleware. Acceptable at the current scale (two use cases); worth revisiting if more delivery-person-restricted endpoints are added later.

### Risks

- If role-restricted routes multiply in future features, this pattern should be revisited in favor of shared middleware — noted here so it isn't rediscovered from scratch.

## Implementation Notes

No repository changes needed for this decision. The blocking dependency (delivery-person credential creation) is separate follow-up work, not part of this feature's implementation.
