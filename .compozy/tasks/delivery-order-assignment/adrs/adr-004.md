# ADR-004: Dedicated Accept/Release Endpoints with Optimistic Concurrency Control

## Status

Accepted

## Date

2026-07-25

## Context

The existing `PATCH /orders/:orderId/:deliveryId` endpoint is a generic status-update path with no ownership validation and no claim-specific rules (e.g., "only if unassigned," "only if not yet picked up"). Overloading it with claim/release semantics would mix distinct business rules into one generic use case. Separately, claiming needs to handle the case where two delivery persons attempt to claim the same order at the same moment.

## Decision

Add two dedicated endpoints, each backed by its own use case:

- `POST /orders/:id/accept` — claims an order. Succeeds only if the order currently has no `deliveryPersonId`.
- `POST /orders/:id/release` — releases a claimed order. Succeeds only if the caller is the current owner and status is `ACCEPTED` (not yet `PICKED_UP`).

The existing `PATCH /orders/:orderId/:deliveryId` endpoint is retained for status progression (`PICKED_UP`, `DELIVERED`, `CANCELED`) but gains an ownership check: the `deliveryId` path parameter must match the `DeliveryPerson` resolved from the authenticated session (ADR-003), rejecting otherwise.

Concurrency for `accept` is handled with an optimistic conditional update: `prisma.subscription.updateMany({ where: { id, deliveryPersonId: null }, data: { deliveryPersonId, status: 'ACCEPTED' } })`. If the affected row count is 0, the order was already claimed by someone else between the client's read of the feed and this request, and the use case throws a `ConflictError`.

## Alternatives Considered

### Alternative 1: Overload the generic PATCH endpoint

- **Description**: Express claim/release as specific `status` payloads on the existing endpoint.
- **Pros**: Fewer new routes.
- **Cons**: Forces the generic use case to special-case "is this a claim, a release, or a plain status change?" and apply different validation per case, inside what is meant to be a simple status-transition handler.
- **Why rejected**: Rejected by the product/technical owner in favor of explicit endpoints during clarification.

### Alternative 2: Explicit transaction with row lock (`SELECT ... FOR UPDATE`) for claim

- **Description**: Wrap the claim check-and-update in a Prisma `$transaction` with a raw `FOR UPDATE` select to serialize concurrent claims.
- **Pros**: More conventional pessimistic-locking approach; guards against a wider class of race conditions.
- **Cons**: Adds manual transaction/raw-SQL code for a race window that is already fully closed by a single atomic conditional `UPDATE ... WHERE deliveryPersonId IS NULL` — Postgres guarantees that update is atomic without any additional locking.
- **Why rejected**: Unnecessary complexity for what the conditional update already solves correctly.

## Consequences

### Positive

- Claim-specific and release-specific business rules live in their own use cases, not entangled with the generic status-update use case.
- The conditional-update approach prevents double-claims without introducing transaction management.

### Negative

- Three endpoints now cover order lifecycle instead of one (`accept`, `release`, and the existing generic `PATCH`), increasing the API surface slightly.

### Risks

- A client retry after a `ConflictError` (409) from `accept` must re-fetch the available feed rather than retry the same order — this must be reflected in the API response contract (clear error message, not a generic 500).

## Implementation Notes

`AcceptOrderUseCase` and `ReleaseOrderUseCase` both depend on `SubscribeRepository` (extended per ADR-002) and `DeliveryUserRepository.findBySupabaseUserId` (ADR-003).
