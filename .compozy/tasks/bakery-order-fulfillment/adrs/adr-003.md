# ADR-003: Máquina de estados única com ator explícito

## Status

Accepted

## Date

2026-09-01

## Context

O ciclo de vida do pedido agora tem transições disparadas por dois atores diferentes: o lojista (`PREPARING`, `READY`, `CANCELED`) e o entregador dono do claim (`ACCEPTED`, `PICKED_UP`, `DELIVERED`, release). Hoje as regras estão espalhadas: `AcceptOrderUseCase` checa `deliveryPersonId: null` no repo, `ReleaseOrderUseCase` checa `status !== 'ACCEPTED'` na mão, `UpdateOrdersUseCase` aceita qualquer `status` do enum sem validar a transição. Sem um ponto único, cada novo endpoint reimplementa (e diverge) as regras.

## Decision

Criar `src/core/usecases/orders/order-status-machine.ts` — função pura, sem dependência de repo:

```ts
type Actor = 'company' | 'delivery';
canTransition(from: OrderStatus, to: OrderStatus, actor: Actor): boolean
assertTransition(from, to, actor): void  // ConflictError se transição inválida; ForbiddenError se ator errado
```

Todos os use cases de transição (`AdvanceOrderByBakeryUseCase`, `AdvanceOrderByCourierUseCase`) chamam `assertTransition` antes de tocar o repositório. `claim`/`release` continuam com o `updateMany` guardado no repo (concorrência), mas também validam a transição pela máquina antes.

## Alternatives Considered

### Regras inline em cada use case

- **Pros**: nada de nova abstração.
- **Cons**: 4+ use cases repetem a matriz de transição; divergência já aconteceu (`UpdateOrdersUseCase` não valida nada).
- **Why rejected**: a matriz de transição é o coração desta feature; precisa de fonte única testável.

## Consequences

### Positive

- Uma tabela de transições, testável isoladamente (sem DB).
- Novos status/atores no futuro mudam um arquivo.

### Negative / Risks

- A guarda de concorrência do `claim` (`where deliveryPersonId: null`) continua vivendo no repo, separada da máquina — a máquina valida "READY→ACCEPTED é legal", o repo garante "só um ganha". Precisa ficar claro nos dois lugares.
