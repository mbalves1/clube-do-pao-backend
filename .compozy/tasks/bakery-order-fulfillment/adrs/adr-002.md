# ADR-002: `bakeryId` desnormalizado em `Order`

## Status

Accepted

## Date

2026-09-01

## Context

Todo endpoint do lojista resolve a `bakeryId` do chamador (`supabaseUserId → User → BakeryPerson → bakeryId`) e precisa filtrar/validar pedidos por essa `bakeryId`. Hoje `Order` só se liga à padaria via `Order → Subscription → bakeryId`. O feed do lojista (`findByBakeryId`) e o check de posse em cada transição fariam join em `subscription` a cada chamada.

## Decision

Adicionar `bakeryId String` em `Order`, preenchido na geração a partir de `subscription.bakeryId`, com relation para `Bakery` e índice `@@index([bakeryId, status])`. O check de posse do lojista compara `order.bakeryId === bakeryId` do chamador diretamente.

## Alternatives Considered

### Sempre juntar via `subscription`

- **Pros**: zero desnormalização; `bakeryId` nunca diverge.
- **Cons**: todo `findByBakeryId` / check de posse precisa de join + `where` aninhado (`subscription: { bakeryId }`); índice composto para o feed fica mais difícil.
- **Why rejected**: o feed do lojista é caminho quente e a `bakeryId` de uma assinatura é imutável na prática — risco de divergência é baixo.

## Consequences

### Positive

- `findByBakeryId` e check de posse são `where: { bakeryId }` simples, cobertos por índice.

### Negative / Risks

- `bakeryId` duplicado entre `order` e `subscription`. Mitigação: só a geração escreve `Order.bakeryId`, sempre a partir de `subscription.bakeryId`; nunca editável depois.
- Migration precisa de `bakeryId` `NOT NULL` na tabela `orders`; poucas linhas legadas → backfill via `subscription.bakeryId` no mesmo migration ou limpeza combinada com o time.
